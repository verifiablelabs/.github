# Contributing to Enthym's GitHub work

Our repositories remain under `verifiablelabs` and retain Verifiable Labs
technical identifiers. Use Enthym in current company prose while preserving
repository URLs, package names, imports, commands, citations, and attribution.

## Start in the owning repository

Read its README, local CONTRIBUTING file, applicable agent instructions, and
workflow definitions. Local guidance takes precedence over these defaults.
Check the branch and working-tree status before editing; keep unrelated work
separate. The [public map](https://github.com/verifiablelabs/vlabs-docs/blob/main/docs/repository-map.md)
helps locate public components. Internal ownership belongs in approved private
records, including the route for reviewing an integration copy.

Small fixes can go directly to a pull request. Open an issue before a broad
behavior change, multi-repository migration, or new research claim. Describe the
problem, desired outcome, and proposed scope without protected content.

## Validation and review

Follow the target repository's actual commands and pinned dependencies. Docs,
Python packages, Lean specifications, evidence artifacts, and Node demos have
different checks. Report exact commands and outcomes, and explain skipped
checks. Do not label a workflow definition as a passing CI run or a saved-record
analysis as a newly reproduced experiment.

For a public claim, link approved public evidence and state the endpoint,
denominators, uncertainty, controls, and limits. Label synthetic demonstrations, historical
measurements, implemented interfaces, and future plans distinctly. Tool reports,
checksums, and selected theorems do not establish independent certification.

Keep private repository names, code, findings, protected evaluation content,
gold answers, raw/customer traces, and credentials out of public issues and PRs.
Use the target repository's security policy for suspected vulnerabilities or
accidental disclosures; see the organization [SECURITY.md](https://github.com/verifiablelabs/.github/blob/main/SECURITY.md)
when no local reporting policy is present.

Check the target repository's license and third-party obligations before
contributing. These defaults grant no new license or permission to publish
private material. Model/provider execution, uploads, deployment, and settings
changes require their own authorized scope and resource budget.
